## Decisões técnicas

- **Estendido `features/admin/`** (`achievements/`, `challenges/`) em vez de criar `features/achievements` e `features/challenges` agora: na 3.5 só existe o lado admin. A Fase 4 cria essas features (vitrine, motor, participação) lendo as mesmas tabelas; o painel continua sendo o único lugar que cadastra.
- **`criteria`/`goal` como JSONB discriminado por `type`**, validados por `z.discriminatedUnion` em `shared/gamification/rules.ts` — compartilhado porque terá três consumidores (painel, motor da 4.1, progresso da 4.2). Chaves extras são descartadas pelo Zod antes de gravar.
- **Referências checadas no banco**: `challenge_complete.challengeId` precisa existir (400); `goal.activityTypeId` precisa ser um tipo **padrão** — desafio é global, tipo custom é de um usuário só (400). Para isso `features/activities` passou a exportar `isDefaultActivityType`.
- **Meta de desafio congelada após o primeiro participante** (409): `user_challenges.progress` está na unidade da meta e trocar a regra no meio invalidaria o ranking. Reenviar a mesma meta é aceito (comparação com `isDeepStrictEqual`, já que o JSONB reordena chaves). Período, nome, recompensa e `isActive` continuam editáveis.
- **`endsAt` exclusivo e `> startsAt`**, validado no POST (refine) e no PATCH sobre os valores mesclados (400). `period` (`upcoming|ongoing|ended`) é calculado na resposta e filtrável via `?period=`.
- **Exclusão restrita**: conquista com desbloqueios → 409 (sumiria do perfil de quem a tem; desative); desafio com participantes ou referenciado por conquista `challenge_complete` → 409.
- **Trocar o critério não revoga desbloqueios** já concedidos.
- **Nome de conquista único** (case-insensitive no service + `@unique` no banco); desafios podem repetir nome (edições recorrentes).
- **`reward` é texto livre** (ex.: "Selo de ouro"); recompensa em forma de conquista se modela com `challenge_complete`.
- **Ícone** segue o fluxo de mídia global da 3.2 (`icon` no corpo, `iconUrl: null` remove).
- **`user_achievements` / `user_challenges` só com estrutura base** (unique `user_id + achievement_id`/`challenge_id`, índices para listagem/ranking). Nenhuma rota escreve nelas ainda — os testes inserem direto.

## APIs

| Método | Rota                              | Descrição                                                            |
| ------ | --------------------------------- | -------------------------------------------------------------------- |
| GET    | `/admin/achievements`             | Paginado, `?q=&status=`, com `unlockCount`                           |
| POST   | `/admin/achievements`             | `{ name, description?, criteria, isActive?, icon? }`                 |
| GET    | `/admin/achievements/:id`         | Detalhe                                                              |
| PATCH  | `/admin/achievements/:id`         | Campos acima + `iconUrl: null`                                       |
| DELETE | `/admin/achievements/:id`         | 204; 409 se já desbloqueada                                          |
| GET    | `/admin/achievements/:id/unlocks` | Paginado, `unlockedAt desc`                                          |
| GET    | `/admin/challenges`               | Paginado, `?q=&status=&period=`, com `participantCount`              |
| POST   | `/admin/challenges`               | `{ name, description?, goal, reward?, startsAt, endsAt, isActive? }` |
| GET    | `/admin/challenges/:id`           | Detalhe                                                              |
| PATCH  | `/admin/challenges/:id`           | Parcial; meta congelada com participantes (409)                      |
| DELETE | `/admin/challenges/:id`           | 204; 409 com participantes ou conquista dependente                   |

## Modelo de dados

- **`achievements`**: `id`, `name` (varchar 120, único), `description` (varchar 500), `icon_url`, `criteria` (jsonb), `is_active`, `created_at`, `updated_at`.
- **`challenges`**: `id`, `name` (varchar 120), `description` (varchar 1000), `goal` (jsonb), `reward` (varchar 255), `starts_at`, `ends_at`, `is_active`, timestamps. Índice `(is_active, starts_at, ends_at)`.
- **`user_achievements`**: `id`, `user_id` (fk cascade), `achievement_id` (fk cascade), `unlocked_at`. Unique `(user_id, achievement_id)`; índice `(achievement_id, unlocked_at)`.
- **`user_challenges`**: `id`, `user_id` (fk cascade), `challenge_id` (fk cascade), `progress` (int), `completed_at`, `joined_at`, `updated_at`. Unique `(user_id, challenge_id)`; índice `(challenge_id, progress, updated_at)` para o ranking da 4.2.

## Como testar

```bash
curl -s -X POST localhost:3333/admin/challenges -H "authorization: Bearer $ADMIN" \
  -H 'content-type: application/json' \
  -d '{"name":"Outubro ativo","goal":{"type":"activity_minutes","minutes":600},"startsAt":"2026-10-01T00:00:00-03:00","endsAt":"2026-11-01T00:00:00-03:00","reward":"Selo Outubro"}'
curl -s -X POST localhost:3333/admin/achievements -H "authorization: Bearer $ADMIN" \
  -H 'content-type: application/json' \
  -d "{\"name\":\"Concluiu Outubro\",\"criteria\":{\"type\":\"challenge_complete\",\"challengeId\":\"$CHALLENGE_ID\"}}"
```

Automatizado (`test/admin-gamification.test.ts`, 26 casos): critérios válidos/inválidos; desafio inexistente; ícone global; 409 de nome; filtros; PATCH com antes/depois; exclusão com/sem desbloqueio; unlocks paginado; metas válidas; tipo custom/inexistente → 400; datas inválidas no POST e PATCH mesclado; `period` e filtro; meta congelada; exclusão de desafio livre/com participante/referenciado.
