## Decisões técnicas

- **Não fiz o item 1.0 do roadmap** (desacoplar Prisma de `fastify.d.ts`/`error-handler`/health) — decisão explícita do time para este PR. `auth.repository.ts` importa o singleton `prisma` de `shared/db/client.ts` diretamente, no mesmo padrão que `shared/media/db-media-storage.ts` já usa (não usa `app.prisma`), então não introduz acoplamento novo além do que já existia.
- **Hash de senha:** `argon2` (argon2id, parâmetros padrão da lib) em vez de bcrypt — recomendação atual da OWASP, resistente a cracking por GPU/ASIC.
- **Email case-insensitive:** normalizado para lowercase em `auth.service.ts` antes de qualquer leitura/escrita; `@unique` simples em `email`. Evita depender de `citext` ou índice de expressão no Postgres.
- **Assinatura de tokens sem `@fastify/jwt`:** `plugins/auth.ts` continua só *verificando* access tokens via `request.jwtVerify()` (nenhuma mudança estrutural). `auth.service.ts` assina access e refresh tokens com `jose` (`SignJWT`, HS256) usando os mesmos secrets (`JWT_ACCESS_SECRET`/`JWT_REFRESH_SECRET`) — é JWT padrão, então o que o `jose` assina verifica normalmente no `@fastify/jwt`. Isso mantém o service sem dependência do Fastify (testável isoladamente) e reaproveita uma única lib (`jose`) tanto para assinar tokens quanto para verificar os id/identity tokens do Google e da Apple via JWKS remoto.
- **Invalidação de refresh token (logout):** sem tabela de sessões. `users.token_version` (int, default 0) é incrementado no logout; o refresh token carrega a claim `tv` no momento da emissão, e `POST /auth/refresh` rejeita (401) se `tv` não bater com o valor atual — invalida todas as sessões do usuário de uma vez, sem precisar rastrear cada token emitido.
- **Checagem de `banned`/`inactive`:** vive em `plugins/auth.ts` (decorator `authenticate`), não em `features/auth/`, porque a regra do roadmap é geral ("em rotas autenticadas", não só `/auth`). Consulta `shared/auth/check-user-status.ts` — vive em `shared/` (não em `plugins/`) porque é um acesso a dado transversal, e `plugins/` não deveria embutir queries de domínio. Custo: 1 SELECT por PK extra em toda requisição autenticada — aceitável, índice de PK.
- **Vinculação OAuth ↔ conta email/senha:** `POST /auth/google`/`/auth/apple` tentam achar por `(oauth_provider, oauth_subject)` primeiro (login repetido), senão por `email` (vincula à conta existente, preservando dados) e só cria usuário novo se nenhum dos dois existir. O cenário "conflito: email OAuth ≠ email da conta logada" do roadmap não se aplica a este conjunto de endpoints — nenhum deles é uma vinculação autenticada (loga com o que quer que o token OAuth diga); ficou documentado aqui como decisão, não implementado.
- **Regras de senha:** mínimo 8 caracteres, ao menos uma letra e um dígito (`auth.schemas.ts`). O roadmap só pedia "regras básicas" sem especificar.
- **Google/Apple exigem apenas o client id** (`GOOGLE_CLIENT_ID`, `APPLE_CLIENT_ID`), não segredo de app: os endpoints só verificam um id/identity token já emitido pelo client (fluxo nativo), não fazem troca client-secret nem chamadas server-to-server — por isso não há `APPLE_TEAM_ID`/`APPLE_KEY_ID`/`APPLE_PRIVATE_KEY`.

## APIs

| Método | Rota           | Descrição                                          |
| ------ | -------------- | --------------------------------------------------- |
| POST   | `/auth`        | Cria conta com email e senha                        |
| POST   | `/auth/login`  | Autentica com email e senha                          |
| POST   | `/auth/google` | Autentica/vincula conta via `id_token` do Google      |
| POST   | `/auth/apple`  | Autentica/vincula conta via `identity_token` da Apple |
| POST   | `/auth/refresh`| Renova o access token                                |
| POST   | `/auth/logout` | Invalida os refresh tokens vigentes (incrementa `token_version`) |
| GET    | `/auth/me`     | Usuário autenticado + perfil resumido                |

## Modelo de dados

**`users`**: `id` (uuid pk), `email` (varchar 255, unique, sempre lowercase), `password_hash` (nullable), `oauth_provider` (enum nullable), `oauth_subject` (varchar nullable), `role` (enum, default `user`), `status` (enum, default `active`), `token_version` (int, default 0), `created_at`, `updated_at`. Único composto `(oauth_provider, oauth_subject)`.

**`user_profiles`**: `user_id` (uuid pk/fk → `users.id`, `onDelete: cascade`), `display_name`, `avatar_url`, `onboarding_completed_at`, `created_at`, `updated_at`.

## Variáveis de ambiente

| Variável           | Descrição                                                           |
| ------------------ | --------------------------------------------------------------------- |
| `GOOGLE_CLIENT_ID`  | `aud` esperado no `id_token` do Google (Google Cloud Console)         |
| `APPLE_CLIENT_ID`   | `aud` esperado no `identity_token` da Apple (bundle id / Services ID) |

(`JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `JWT_ACCESS_TTL`, `JWT_REFRESH_TTL` já existiam desde a Fase 0.)

## Como testar

```bash
yarn db:up && yarn db:migrate && yarn dev

# Register
curl -s -X POST localhost:3333/auth -H 'content-type: application/json' \
  -d '{"email":"Test.User@Example.com","password":"senha123","displayName":"Test User"}'
# -> 201, accessToken/refreshToken, email normalizado para lowercase

# Register duplicado
curl -s -X POST localhost:3333/auth -H 'content-type: application/json' \
  -d '{"email":"test.user@example.com","password":"senha123"}'
# -> 409 CONFLICT

# Login
curl -s -X POST localhost:3333/auth/login -H 'content-type: application/json' \
  -d '{"email":"test.user@example.com","password":"senha123"}'
# -> 200, mesmo user.id do register

# Me
curl -s localhost:3333/auth/me -H "authorization: Bearer $ACCESS"
# -> 200

# Refresh
curl -s -X POST localhost:3333/auth/refresh -H 'content-type: application/json' \
  -d "{\"refreshToken\":\"$REFRESH\"}"
# -> 200, novo accessToken

# Logout, depois tentar o refresh antigo de novo
curl -s -X POST localhost:3333/auth/logout -H "authorization: Bearer $ACCESS"
curl -s -X POST localhost:3333/auth/refresh -H 'content-type: application/json' \
  -d "{\"refreshToken\":\"$REFRESH\"}"
# -> 401 ("Sessao invalidada")
```

Todos os fluxos acima (register → login → me → refresh → logout → refresh recusado, senha errada → 401, senha fraca → 400, e status `banned` bloqueando tanto o login quanto uma requisição autenticada em andamento) foram executados manualmente durante a implementação. Fluxo Google/Apple depende de um `id_token`/`identity_token` real de um client configurado — não testado ponta a ponta neste PR (ver Pendências).
