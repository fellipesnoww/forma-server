## Decisões técnicas

- **Fuso no perfil, não na query**: o dia de um registro precisa ser o mesmo no calendário, no detalhe e nos gráficos (2.4). Guardar em `user_profiles.timezone` evita que cada tela mande um fuso diferente. Default `America/Sao_Paulo` porque o produto é pt-BR; o client deve gravar o fuso do aparelho no onboarding (`PATCH /profile { timezone }`).
- **Validação IANA via `Intl`** (`shared/validation/timezone.ts`): o que o runtime aceita o Postgres também entende em `AT TIME ZONE`. Abreviações como `GMT-3` ou nomes inexistentes → 400.
- **Conversão de fuso no SQL**: os limites do período (início do 1º dia e do dia seguinte ao último, locais) viram instantes UTC num CTE `bounds` (`shared/db/local-range.ts`); o `WHERE` filtra `performed_at` por esses instantes, então os índices `(user_id, performed_at)` de `workout_sessions` e `free_activities` continuam sendo usados. Só o `GROUP BY` converte para o fuso. Horário de verão fica a cargo do Postgres.
- **Agregação mensal numa query** (`UNION ALL` das duas tabelas + `GROUP BY` dia local), com `photoUrls` via `array_agg(... ORDER BY performed_at)` fatiado em `[1:N]` no próprio SQL — o payload não carrega fotos que o client não vai exibir.
- **Só dias com registro** em `days`: o client já sabe montar a grade do mês; mandar 28–31 objetos vazios só infla a resposta.
- **Detalhe do dia reaproveita as features donas dos dados**: `features/workout-sessions` e `features/activities` exportam `getSessionsBetween`/`getActivitiesBetween` e os schemas de resposta pelo `index.ts`. O item de sessão é o mesmo da listagem (sem `exercises`); o detalhe completo continua em `GET /workout-sessions/:id`.
- **Dia vazio → 200** com listas vazias, não 404: o client pode abrir qualquer dia do calendário.
- **Sessões contam mesmo sem `complete`**: o calendário mostra o que foi registrado, não só o que foi finalizado.

## APIs

| Método | Rota              | Descrição                                                                        |
| ------ | ----------------- | -------------------------------------------------------------------------------- |
| GET    | `/calendar`       | `?year=&month=` → `{ year, month, timezone, photoLimit, days[] }`                |
| GET    | `/calendar/:date` | `{ date, timezone, hasWorkout, hasActivity, summary, workouts[], activities[] }` |
| PATCH  | `/profile`        | Passa a aceitar `timezone` (IANA)                                                |

`summary` = `{ workoutCount, activityCount, activityMinutes }`.

## Modelo de dados

**`user_profiles`** (alterada): `timezone` varchar(64) not null default `'America/Sao_Paulo'`.

## Variáveis de ambiente

| Variável                  | Descrição                                                   |
| ------------------------- | ----------------------------------------------------------- |
| `CALENDAR_MAX_THUMBNAILS` | Máximo de `photoUrls` por dia no mês (default 3; 0 desliga) |

## Como testar

```bash
curl -s -X PATCH localhost:3333/profile -H "authorization: Bearer $ACCESS" \
  -H 'content-type: application/json' -d '{"timezone":"America/Sao_Paulo"}'
curl -s "localhost:3333/calendar?year=2026&month=10" -H "authorization: Bearer $ACCESS"
curl -s localhost:3333/calendar/2026-10-03 -H "authorization: Bearer $ACCESS"
```

Automatizado (`test/calendar.test.ts`): fuso default e `PATCH` válido/inválido; agrupamento por dia local
com registros às 23h locais (em UTC já é o dia seguinte) nas viradas de dia e de mês; flags e `summary`
combinando treino e atividades; limite de 3 miniaturas, mais antigas primeiro; mês vazio; troca de fuso
muda o dia; detalhe do dia com bordas 23:59/00:00 e ordenação; detalhe bate com a agregação mensal;
dia vazio → 200; queries e datas inválidas → 400. Mutation check: agrupar em UTC em vez do fuso do perfil
derruba 4 casos.

## Pendências

- Sem teste de carga das agregações — item da 2.5.
- Calendário só lê o fuso do perfil; se o usuário viajar, os dias seguem o fuso salvo até ele trocar.
- `photoUrls` aponta para `GET /media/:id` em tamanho original (sem miniatura gerada no servidor) — mesmo descope de compressão da 1.2/1.5/2.1.
