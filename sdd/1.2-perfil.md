## Decisões técnicas

- **`PATCH /profile` vs `POST /profile/measurements`:** dois caminhos de escrita para as mesmas colunas. `PATCH /profile` corrige o snapshot atual direto (ex.: editar um valor digitado errado), sem gerar linha de histórico. `POST /profile/measurements` é o fluxo de "registrar uma nova pesagem": grava em `body_measurements` **e** sincroniza `user_profiles` na mesma operação — é o único endpoint que cria histórico, evitando que o histórico vire uma cópia de toda edição do perfil.
- **Sincronização atômica:** `profile.repository.ts#createMeasurement` usa `prisma.$transaction([...])` (batch, não `$transaction(async (tx) => ...)`) porque as duas escritas (insert em `body_measurements`, update em `user_profiles`) não dependem do resultado uma da outra — a forma de array é suficiente e mais simples.
- **Campos parciais em `body_measurements`:** todas as colunas de medida são nullable e o body aceita qualquer subconjunto (`superRefine` exige só que pelo menos uma venha preenchida). `PATCH /profile` e `POST /profile/measurements` compartilham esse mesmo formato de body (`measurementFieldsSchema`), então um objeto `{ weightKg: 79 }` some com `heightCm`/`waistCm`/`chestCm` — o Prisma `update`/`create` só grava as chaves presentes, os demais campos ficam com o valor anterior (ou `null` na criação da linha de histórico).
- **Tipo numérico:** `Float` (double precision) nas quatro colunas de medida, não `Decimal` — o domínio (peso/altura/circunferência em kg/cm, 1 casa decimal na prática) não tem os requisitos de precisão exata que justificariam `Decimal` (esse é reservado a dinheiro no roadmap). Menos tipo especial para (de)serializar entre Prisma/Zod/JSON.
- **Paginação do histórico:** `{ items, total, page, limit }`, mesmo envelope descrito na convenção "Paginação admin" do roadmap — reaproveitado aqui porque é o único formato de lista paginada já documentado no projeto; `GET /profile/measurements` aceita `page`/`limit` além de `from`/`to`.
- **Avatar sem resize/limite dedicado:** o roadmap pede resize 512×512 e teto de ~2 MB. `MediaService` (Fase 0) não tem resize — já era descope explícito da Fase 0 ("resize/WebP fora de escopo"). `POST /profile/avatar` reaproveita `dbMediaStorage.upload` como está, validando só o limite global `MEDIA_MAX_SIZE_MB` (5 MB por padrão). Implementar um teto de 2 MB só para avatar exigiria duplicar a lógica de decodificação de `media.validation.ts` (ela já calcula o tamanho antes de alocar o buffer) ou estender `MediaUploadInput` com um limite por chamada — nenhum dos dois foi feito neste PR; ver Pendências.
- **`requireProfile`:** todo endpoint da feature busca o perfil antes de escrever/ler porque, embora `createUserWithProfile` (Fase 1.1) sempre crie a linha em `user_profiles` junto com o `users`, um 404 explícito é mais barato de diagnosticar do que um erro de FK genérico se essa garantia algum dia quebrar.

## APIs

| Método | Rota                    | Descrição                                               |
| ------ | ----------------------- | ------------------------------------------------------- |
| GET    | `/profile`              | Perfil + medidas atuais                                 |
| PATCH  | `/profile`              | Atualiza nome e/ou medidas atuais (sem gerar histórico) |
| POST   | `/profile/avatar`       | Upload de avatar em base64, retorna `avatarUrl`         |
| GET    | `/profile/measurements` | Histórico paginado (`?from=&to=&page=&limit=`)          |
| POST   | `/profile/measurements` | Registra medida: cria histórico e sincroniza o perfil   |

## Modelo de dados

**`user_profiles`** (alterada): + `weight_kg`, `height_cm`, `waist_cm`, `chest_cm` (todos `double precision`, nullable).

**`body_measurements`** (nova): `id` (uuid pk), `user_id` (uuid fk → `users.id`, `onDelete: cascade`), `weight_kg`, `height_cm`, `waist_cm`, `chest_cm` (nullable), `created_at`. Índice `(user_id, created_at)` para o histórico paginado.

## Variáveis de ambiente

Nenhuma nova. Reaproveita `MEDIA_MAX_SIZE_MB`, `MEDIA_ALLOWED_MIME_TYPES`, `MEDIA_PUBLIC_BASE_URL` (Fase 0) para o upload de avatar.

## Como testar

```bash
yarn db:up && yarn db:migrate && yarn dev

# Login (usa uma conta já registrada — ver sdd/1.1-autenticacao.md)
ACCESS=$(curl -s -X POST localhost:3333/auth/login -H 'content-type: application/json' \
  -d '{"email":"test.user@example.com","password":"senha123"}' | node -pe 'JSON.parse(require("fs").readFileSync(0)).accessToken')

# Perfil vazio
curl -s localhost:3333/profile -H "authorization: Bearer $ACCESS"

# PATCH nome + peso
curl -s -X PATCH localhost:3333/profile -H "authorization: Bearer $ACCESS" \
  -H 'content-type: application/json' -d '{"displayName":"Test User","weightKg":80}'

# PATCH valor negativo -> 400
curl -s -X PATCH localhost:3333/profile -H "authorization: Bearer $ACCESS" \
  -H 'content-type: application/json' -d '{"weightKg":-5}'

# PATCH corpo vazio -> 400 ("Envie ao menos um campo")
curl -s -X PATCH localhost:3333/profile -H "authorization: Bearer $ACCESS" \
  -H 'content-type: application/json' -d '{}'

# Registra medida (cria histórico + sincroniza perfil)
curl -s -X POST localhost:3333/profile/measurements -H "authorization: Bearer $ACCESS" \
  -H 'content-type: application/json' -d '{"weightKg":79.5,"heightCm":180}'
curl -s -X POST localhost:3333/profile/measurements -H "authorization: Bearer $ACCESS" \
  -H 'content-type: application/json' -d '{"weightKg":79}'

# Confere sincronizacao: heightCm permanece 180, weightKg vira 79
curl -s localhost:3333/profile -H "authorization: Bearer $ACCESS"

# Histórico paginado
curl -s "localhost:3333/profile/measurements?limit=10" -H "authorization: Bearer $ACCESS"

# Avatar (PNG 1x1 em base64)
curl -s -X POST localhost:3333/profile/avatar -H "authorization: Bearer $ACCESS" \
  -H 'content-type: application/json' \
  -d '{"data":"<base64>","mimeType":"image/png","filename":"avatar.png"}'
curl -s localhost:3333/profile -H "authorization: Bearer $ACCESS"
```

Todos os fluxos acima (GET vazio, PATCH nome+medida, PATCH negativo → 400, PATCH corpo vazio → 400,
duas chamadas de `POST /profile/measurements` com sincronização parcial confirmada, histórico
paginado, upload de avatar com atualização de `avatarUrl`) foram executados manualmente durante a
implementação.
