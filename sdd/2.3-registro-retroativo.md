# 2.3 Registro retroativo

> Roadmap: [roadmap-backend.md](../roadmap-backend.md) › Fase 2 › 2.3 Registro retroativo
> Data: 2026-10-03
>
> Regra transversal: vale para sessões (1.5) e atividades (2.1). O "dia" de um registro
> retroativo é definido pelo fuso do perfil (2.2).

## Escopo entregue

- [x] `performedAt <= now()` com 5 min de tolerância de relógio — já existia na 1.5; agora em `shared/validation/performed-at.ts`
- [x] Mesma validação em sessões e atividades (POST e PATCH)
- [x] Limite retroativo opcional via env: `RETROACTIVE_MAX_DAYS`
- [x] Testes: data futura rejeitada (`workout-sessions.test.ts`, `activities.test.ts`)
- [x] Testes: meia-noite e fuso (`calendar.test.ts`, `retroactive.test.ts`)
- [x] OpenAPI: a descrição de `performedAt` em todas as rotas afetadas diz se há limite e qual

## Decisões técnicas

- **Uma regra só**: `performedAtSchema` em `shared/validation/` é importado pelas duas features e acrescentado à descrição de cada uma. Mudar a regra muda sessões e atividades juntas.
- **Limite como janela móvel de N × 24h** (`isWithinRetroactiveLimit`), não "N dias de calendário": não depende do fuso do usuário e não muda de resultado à meia-noite. A diferença é de no máximo um dia na borda.
- **Sem limite por padrão** (`RETROACTIVE_MAX_DAYS` vazio): o roadmap diz "opcional", e o caso de uso principal (lançar o treino de ontem que esqueceu) não precisa dele. O valor é lido no boot, como o resto do `env`.
- **Meia-noite e fuso não são regra de validação**, e sim de agrupamento: o servidor guarda o instante UTC; o dia em que o registro aparece é calculado no calendário/progressão com o fuso do perfil (ver 2.2). O client deve enviar `performedAt` com offset (`2025-03-10T23:30:00-03:00`), o que já era aceito desde a 1.5.
- **`yarn test` roda com `RETROACTIVE_MAX_DAYS=3650`** para exercitar o limite de ponta a ponta; os demais testes usam datas de 2024–2025, dentro dessa janela.

| Variável               | Descrição                                                        |
| ---------------------- | ---------------------------------------------------------------- |
| `RETROACTIVE_MAX_DAYS` | Máximo de dias no passado para `performedAt`. Vazio = sem limite |

## Como testar

```bash
RETROACTIVE_MAX_DAYS=90 yarn dev
curl -s -X POST localhost:3333/activities -H "authorization: Bearer $ACCESS" \
  -H 'content-type: application/json' \
  -d "{\"activityTypeId\":\"$TYPE_ID\",\"durationMinutes\":30,\"performedAt\":\"2020-01-01T10:00:00-03:00\"}"
# -> 400 VALIDATION_ERROR
```

Automatizado (`test/retroactive.test.ts`): dentro do limite aceito e além do limite rejeitado em POST e
PATCH das duas features; limite citado no OpenAPI; borda exata da janela; datas locais (29/02, virada de
ano, dezembro → janeiro, "hoje" em São Paulo/UTC/Tóquio). Mutation check: desligar o limite derruba 2 casos.

## Pendências

- O limite não se aplica a `body_measurements`: medidas não aceitam data retroativa (o `createdAt` é sempre o do servidor).
