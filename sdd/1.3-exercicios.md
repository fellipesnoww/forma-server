## Decisões técnicas

- **Catálogo (`Exercise`) e custom (`CustomExercise`) como tabelas separadas**, não uma tabela única com `user_id` nullable: o catálogo é global e só admin edita (Fase 3), enquanto custom é sempre isolado por usuário. Modelos separados evitam uma query com `WHERE user_id = X OR user_id IS NULL` espalhada por toda a feature e deixam o soft delete (só existe em custom) explícito no schema.
- **`GET /exercises` funde os dois catálogos na service** (`Promise.all` + merge em memória), não uma `UNION` SQL: o volume por usuário é pequeno (catálogo fixo + poucos customs), e resolver em duas queries tipadas do Prisma é mais simples que uma raw query para um DTO comum (`source: 'catalog' | 'custom'`).
- **`Exercise.name` único**: existia o risco de o seed rodar mais de uma vez e duplicar linhas. Um `@@unique([name])` permite `upsert` idempotente sem precisar de uma chave de negócio separada (ex.: slug de exercício) — o catálogo não tem outro identificador natural.
- **Exclusão do custom exercise é soft delete**, porque `sheet_exercises` (1.4) pode referenciar um `custom_exercise_id`; apagar a linha de verdade quebraria planilhas existentes.
- **`resolveMuscleGroupId`**: `muscleGroupSlug` inválido em `POST/PATCH /exercises/custom` retorna 400 imediatamente (antes de tocar o banco) — evita um `customExercise` órfão com `muscle_group_id` de um grupo que não existe (não há FK reversa para checar isso automaticamente sem esse guard).
- **Ownership de custom exercise**: 404 se não existe/já deletado, 403 se existe mas pertence a outro usuário — diferente de `workout-sheets`, aqui a distinção importa porque `PATCH`/`DELETE /exercises/custom/:id` recebem o id direto na URL (não filtrado implicitamente por `userId` na query), então faz sentido informar "não é seu" separado de "não existe".
- **`exerciseRefExists` exportado pelo `index.ts`**: é o único ponto de acesso que `features/workout-sheets` tem à feature `exercises`, seguindo a convenção "queries de outra feature passam pelo service público" — `workout-sheets` nunca importa `exercises.repository.ts`.

## APIs

| Método | Rota                    | Descrição                                             |
| ------ | ----------------------- | ----------------------------------------------------- |
| GET    | `/exercises`            | Catálogo ativo + custom (`?muscleGroup=&q=`)          |
| POST   | `/exercises/custom`     | Cria exercício personalizado                          |
| PATCH  | `/exercises/custom/:id` | Edita exercício personalizado (somente dono)          |
| DELETE | `/exercises/custom/:id` | Soft delete de exercício personalizado (somente dono) |

## Modelo de dados

**`muscle_groups`** (nova): `id` (uuid pk), `name` (varchar 80), `slug` (varchar 80, unique).

**`exercises`** (nova): `id` (uuid pk), `name` (varchar 160, unique), `muscle_group_id` (uuid fk nullable → `muscle_groups.id`), `is_active` (bool, default true), `media_url` (nullable), `female_media_url` (nullable, variante com executora feminina — adicionada depois, ver 3.2), `created_at`, `updated_at`. Índice `(muscle_group_id)`.

**`custom_exercises`** (nova): `id` (uuid pk), `user_id` (uuid fk → `users.id`, `onDelete: cascade`), `name` (varchar 160), `muscle_group_id` (uuid fk nullable), `deleted_at` (nullable), `created_at`, `updated_at`. Índice `(user_id, deleted_at)`.

## Como testar

```bash
yarn db:up && yarn db:migrate && yarn db:seed && yarn dev

ACCESS=$(curl -s -X POST localhost:3333/auth/login -H 'content-type: application/json' \
  -d '{"email":"test.user@example.com","password":"senha123"}' | node -pe 'JSON.parse(require("fs").readFileSync(0)).accessToken')

# Catalogo (88 itens)
curl -s localhost:3333/exercises -H "authorization: Bearer $ACCESS" | node -pe 'JSON.parse(require("fs").readFileSync(0)).items.length'

# Filtro por grupo muscular
curl -s -G localhost:3333/exercises --data-urlencode "muscleGroup=peito" -H "authorization: Bearer $ACCESS"

# Busca por nome
curl -s -G localhost:3333/exercises --data-urlencode "q=supino" -H "authorization: Bearer $ACCESS"

# Cria custom
curl -s -X POST localhost:3333/exercises/custom -H "authorization: Bearer $ACCESS" \
  -H 'content-type: application/json' -d '{"name":"Remada invertida na TRX","muscleGroupSlug":"costas"}'

# Grupo muscular invalido -> 400
curl -s -X POST localhost:3333/exercises/custom -H "authorization: Bearer $ACCESS" \
  -H 'content-type: application/json' -d '{"name":"X","muscleGroupSlug":"nao-existe"}'

# Edita e depois remove (soft delete); some da listagem em seguida
curl -s -X PATCH localhost:3333/exercises/custom/<id> -H "authorization: Bearer $ACCESS" \
  -H 'content-type: application/json' -d '{"name":"Remada invertida TRX v2"}'
curl -s -X DELETE localhost:3333/exercises/custom/<id> -H "authorization: Bearer $ACCESS"
```

Cenários acima (catálogo com 88 itens, filtro por grupo, busca, criação/edição/soft-delete de custom,
grupo muscular inválido rejeitado, isolamento entre usuários) foram verificados manualmente durante
a implementação.
