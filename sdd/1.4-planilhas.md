## Decisões técnicas

- **Exclusividade `exerciseId` XOR `customExerciseId` validada na aplicação, não via `CHECK` no Postgres**: o Prisma schema não gera `CHECK` constraints a partir do `schema.prisma`; escrever a constraint via SQL manual duplicaria a mesma regra que a service já precisa aplicar para checar posse do `customExerciseId` (isso não dá pra validar só com SQL). A regra fica um único lugar: `sheetExerciseInputSchema.superRefine` (schema) + `exerciseRefExists` (service, cross-feature). Ver Pendências.
- **`PATCH /workout-sheets/:id` substitui dias/exercícios por completo** (`sheetDay.deleteMany` + recriação, dentro de uma transação) em vez de diff granular: o roadmap não pede merge parcial de dias, e reconciliar `sortOrder`/`weekday` contra o estado anterior exigiria uma segunda estrutura de dados só para diffing. `days` é opcional no body — se omitido, só `name` muda.
- **`PATCH /workout-sheets/:id/reorder` é um endpoint separado** (não parte do `PATCH` genérico) porque reordenar é uma operação sobre um único dia (todos os `sheetExercise.id` precisam pertencer ao mesmo `dayId`), enquanto o `PATCH` genérico substitui a planilha inteira — misturar os dois exigiria uma forma de payload híbrida sem ganho real.
- **Ownership via filtro na query, não checagem separada**: toda leitura/escrita usa `where: { id, userId, deletedAt: null }`; um id de outro usuário simplesmente não bate a query e vira 404 — não existe um branch de código dedicado a "403 dono errado" (mesma decisão do roadmap: "ownership: planilha pertence ao usuário autenticado").
- **`exerciseRefExists` consumido via `features/exercises/index.ts`**, nunca `exercises.repository.ts` direto — respeita a convenção de export público entre features; é a única forma de `workout-sheets` "ver" dados de `exercises`.
- **Nome do exercício resolvido via `include` do Prisma** (`exercise: true, customExercise: true` em `SheetExercise`) em vez de uma segunda query de lookup: os relations já existem no schema para a validação de referência, então reaproveitar o mesmo include no detalhe da planilha evita N+1 sem introduzir uma tabela desnormalizada.
- **`targetSets`/`targetReps` opcionais em `sheet_exercises`**: o roadmap só pede "defaults" sem especificar o formato; sets/reps alvo é o mínimo que a Fase 1.5 (sessão de treino) precisa para sugerir valores iniciais, sem inventar campos (ex.: peso alvo) que nenhum item do roadmap pede ainda.

## APIs

| Método | Rota                          | Descrição                                                    |
| ------ | ----------------------------- | ------------------------------------------------------------ |
| GET    | `/workout-sheets`             | Lista planilhas do usuário (resumo)                          |
| POST   | `/workout-sheets`             | Cria planilha + dias + exercícios                            |
| GET    | `/workout-sheets/:id`         | Detalhe completo (dias + exercícios com nome resolvido)      |
| PATCH  | `/workout-sheets/:id`         | Atualiza nome e/ou substitui dias + exercícios               |
| DELETE | `/workout-sheets/:id`         | Soft delete                                                  |
| PATCH  | `/workout-sheets/:id/reorder` | Reordena exercícios de um dia (`dayId` + lista de sortOrder) |

## Modelo de dados

**`workout_sheets`** (nova): `id` (uuid pk), `user_id` (uuid fk → `users.id`, `onDelete: cascade`), `name` (varchar 120), `deleted_at` (nullable), `created_at`, `updated_at`. Índice `(user_id, deleted_at)`.

**`sheet_days`** (nova): `id` (uuid pk), `sheet_id` (uuid fk → `workout_sheets.id`, `onDelete: cascade`), `weekday` (int, 0–6), `order` (int), `created_at`. Único `(sheet_id, weekday)`.

**`sheet_exercises`** (nova): `id` (uuid pk), `day_id` (uuid fk → `sheet_days.id`, `onDelete: cascade`), `exercise_id` (uuid fk nullable → `exercises.id`), `custom_exercise_id` (uuid fk nullable → `custom_exercises.id`), `sort_order` (int), `target_sets` (int nullable), `target_reps` (int nullable). Índice `(day_id, sort_order)`.

## Como testar

```bash
yarn db:up && yarn db:migrate && yarn db:seed && yarn dev

ACCESS=$(curl -s -X POST localhost:3333/auth/login -H 'content-type: application/json' \
  -d '{"email":"test.user@example.com","password":"senha123"}' | node -pe 'JSON.parse(require("fs").readFileSync(0)).accessToken')

CATALOG_ID=$(curl -s -G localhost:3333/exercises --data-urlencode "q=Supino reto com barra" \
  -H "authorization: Bearer $ACCESS" | node -pe 'JSON.parse(require("fs").readFileSync(0)).items[0].id')

# Cria planilha com 2 dias
curl -s -X POST localhost:3333/workout-sheets -H "authorization: Bearer $ACCESS" \
  -H 'content-type: application/json' -d "{\"name\":\"Treino ABC\",\"days\":[
    {\"weekday\":1,\"order\":0,\"exercises\":[{\"exerciseId\":\"$CATALOG_ID\",\"sortOrder\":0,\"targetSets\":4,\"targetReps\":10}]},
    {\"weekday\":3,\"order\":1,\"exercises\":[{\"exerciseId\":\"$CATALOG_ID\",\"sortOrder\":0}]}
  ]}"

# weekday duplicado -> 400
# exerciseId + customExerciseId juntos -> 400
# exerciseId inexistente -> 400 ("nao encontrado ou nao pertence ao usuario")
# outro usuario acessando a planilha -> 404
# reorder, patch (nome e/ou dias), delete -> ver respostas completas registradas durante a implementação
```

Cenários executados manualmente: criação com múltiplos dias/exercícios, listagem, detalhe,
`weekday` duplicado rejeitado, referência dupla (`exerciseId`+`customExerciseId`) rejeitada,
`exerciseId` inexistente rejeitado, isolamento entre usuários (planilha e custom exercise de um
usuário são 404/400 para outro), reorder dentro de um dia, `PATCH` só de nome, soft delete seguido
de 404 no `GET`.
