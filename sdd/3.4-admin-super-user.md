# 3.4 Gestão de administradores (super user)

> Roadmap: [roadmap-backend.md](../roadmap-backend.md) › Fase 3 › 3.4 Gestão de administradores (super user)
> Data: 2026-10-04

## Escopo entregue

- [x] `GET /admin/admins` — admins e super_users, paginado
- [x] `PATCH /admin/admins/:id/role` — promove admin → super_user, rebaixa super_user → admin, revoga (→ `user`)
- [x] `GET /admin/audit-logs` — log paginado com filtros
- [x] Documentação OpenAPI (tag `Admin`) e testes (`test/admin-users.test.ts`)

## Decisões técnicas

- **Escopo super_user** (ver 3.1): as três rotas vivem no plugin filho com `requireRole('super_user')`; o service de papel repete a checagem como defesa em profundidade.
- **Mesmo service da 3.3** (`changeUserRole`, escopo `'admins'`): alvo precisa já ser admin/super_user, senão 404 "Administrador não encontrado" — esta rota não serve para promover usuário comum (isso é `PATCH /admin/users/:id/role`). Própria conta → 403; papel igual → no-op; promover a super_user exige conta ativa (409).
- **Rebaixamento vale no próximo request** do alvo, porque `authenticate` lê o papel do banco (3.1). Não é preciso revogar tokens.
- **`GET /admin/admins`** reaproveita `listUsers` com `roles: ['admin','super_user']`; `?role=` restringe a um dos dois, `?q=`/`?status=` como em `/admin/users`.
- **Filtros de audit log em camelCase** (`actorId`, `targetType`, `targetId`) em vez do `actor_id` do roadmap — o resto da API usa camelCase em query (`exerciseId`, `muscleGroup`). `action` e `targetType` são enums fechados (valor fora → 400). `from`/`to` inclusivos sobre `createdAt`; ordenação `createdAt desc, id desc`. Cada item traz `actor: { id, email } | null`.

## APIs

| Método | Rota                     | Descrição                                                        |
| ------ | ------------------------ | ---------------------------------------------------------------- |
| GET    | `/admin/admins`          | `?q=&role=admin\|super_user&status=&page=&limit=`                |
| PATCH  | `/admin/admins/:id/role` | `{ role: user\|admin\|super_user, reason? }`                     |
| GET    | `/admin/audit-logs`      | `?actorId=&action=&targetType=&targetId=&from=&to=&page=&limit=` |

## Modelo de dados

Usa `admin_audit_logs` (3.1) e `users.role`.

## Variáveis de ambiente

Nenhuma nova.

## Como testar

```bash
curl -s -X PATCH localhost:3333/admin/admins/$ID/role -H "authorization: Bearer $SUPER" \
  -H 'content-type: application/json' -d '{"role":"super_user"}'
curl -s "localhost:3333/admin/audit-logs?action=user.role_changed" -H "authorization: Bearer $SUPER"
```

Automatizado: lista e filtro por papel; promoção + rebaixamento com dois logs em ordem; revogação derruba `/admin`; alvo comum/inexistente → 404; própria conta → 403; admin → 403 em GET e PATCH; audit-logs filtrado por ator/ação/alvo, ordenado desc, `from` no futuro → 0, ação inválida → 400.
