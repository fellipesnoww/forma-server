## Decisões técnicas

- **Uma feature, dois prefixos**: `activity-types` só existe para alimentar `activities`, então ambos vivem em `features/activities/`; `index.ts` registra `/activity-types` e `/activities`.
- **Tipos padrão e custom na mesma tabela**: `user_id IS NULL` = padrão (seed); preenchido = personalizado, visível só ao dono. Evita union de duas tabelas na listagem e mantém um FK único em `free_activities`. O seed faz upsert por `slug` (null nos custom — Postgres aceita vários nulls num unique).
- **Nome de tipo único entre os visíveis ao usuário** (case-insensitive, com `trim`): criar "corrida" ao lado do "Corrida" padrão ou repetir um custom → 409 `CONFLICT`. Usuários diferentes podem ter custom com o mesmo nome. Checado na aplicação, sem índice (ver Pendências).
- **Referência de tipo inválida → 400** (inexistente ou custom de outro usuário), mesma regra das referências a exercício na 1.4/1.5. Atividade de outro usuário por id → 404.
- **`durationMinutes` obrigatório, inteiro de 1 a 1440**: o roadmap de features lista duração como campo da atividade; acima de 24h é quase certamente erro de digitação.
- **`performedAt` extraído para `src/shared/validation/`**: a regra (ISO com offset, passado permitido, futuro rejeitado com 5 min de tolerância) agora é uma só entre sessões e atividades — antecipa o item "Validação aplicada em sessões e atividades" da 2.3. `workout-sessions.schemas.ts` passou a importar dali (comportamento inalterado).
- **Foto igual à 1.5**: upload base64 em `POST /:id/photo`; no `PATCH`, `photoUrl` só aceita `null` (remoção) para o client não apontar a atividade para mídia de outro usuário.
- **`DELETE` físico**: nada referencia uma atividade, então não há motivo para soft delete. Exclusão concorrente cai no P2025 → 404 do handler global.
- **FK `activity_type_id` em cascade**: tipos custom só somem junto com o usuário (não há rota de exclusão de tipo). Com `RESTRICT`, o cascade de `users` poderia falhar ao apagar o tipo antes das atividades que o usam.
- **Listagem `?from=&to=` paginada** (`page`/`limit`, máx. 100, `performedAt desc`), no mesmo formato de `GET /workout-sessions`.

## APIs

| Método | Rota                     | Descrição                                                           |
| ------ | ------------------------ | ------------------------------------------------------------------- |
| GET    | `/activity-types`        | Tipos padrão + personalizados do usuário (`source`)                 |
| POST   | `/activity-types/custom` | Cria tipo personalizado (409 se o nome já existe entre os visíveis) |
| GET    | `/activities`            | Histórico paginado (`?from=&to=&page=&limit=`)                      |
| POST   | `/activities`            | Registra atividade (`activityTypeId`, `durationMinutes`, ...)       |
| GET    | `/activities/:id`        | Detalhe                                                             |
| PATCH  | `/activities/:id`        | Atualiza tipo, data, duração, comentário e/ou remove a foto         |
| DELETE | `/activities/:id`        | Remove (físico)                                                     |
| POST   | `/activities/:id/photo`  | Upload base64 da foto, retorna `{ photoUrl }`                       |

## Modelo de dados

**`activity_types`** (nova): `id` (uuid pk), `user_id` (fk nullable → `users.id`, cascade), `slug` (varchar 80, único, nullable), `name` (varchar 80), `created_at`. Índice `(user_id)`.

**`free_activities`** (nova): `id` (uuid pk), `user_id` (fk → `users.id`, cascade), `activity_type_id` (fk → `activity_types.id`, cascade), `performed_at` (timestamptz, default `now()`), `duration_minutes` (int), `comment` (varchar 1000, nullable), `photo_url` (nullable), `created_at`, `updated_at`. Índices `(user_id, performed_at)` e `(activity_type_id)`.

## Pendências

- Unicidade de nome de tipo sem índice: duas criações concorrentes com o mesmo nome podem passar. Um índice parcial `(user_id, lower(name))` não cobriria a colisão com tipos padrão; fica para quando houver edição/admin de tipos (Fase 3).
- Sem rotas de edição/remoção de tipo personalizado — o roadmap não pede.
- Foto sem compressão/resize e mídia anterior não apagada ao trocar/remover foto ou excluir a atividade — mesmo descope da 1.2/1.5.
- Limite retroativo opcional via env fica para a 2.3.
