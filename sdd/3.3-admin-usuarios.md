- [x] `GET /admin/users` — paginado, `?q=&status=&role=`

- [x] `PATCH /admin/users/:id/status` — `active` | `inactive` | `banned`
- [x] `PATCH /admin/users/:id/role` (super_user) — promove `user` → `admin`
- [x] Regra: admin não altera admin/super_user; ninguém altera a própria conta
- [x] Audit log de status e papel
- [x] Documentação OpenAPI (tag `Admin`) e testes (`test/admin-users.test.ts`)

## Decisões técnicas

- **`canManage(actorRole, targetRole)`** em `admin-users.service.ts`: super_user gerencia qualquer conta; admin só contas `user`. Violação → 403 sem audit log. Alterar a própria conta (status ou papel) → 403 — isso também garante que sempre sobra ao menos um super_user ativo (quem age).
- **`SELECT ... FOR UPDATE` no alvo** (`lockUser`) dentro da transação: duas mudanças concorrentes no mesmo usuário serializam, e a regra é avaliada sobre o papel vigente.
- **Banir/desativar incrementa `tokenVersion`** (mesmo mecanismo do logout). O access token já cai no próximo request porque `authenticate` confere o status; o incremento garante que refresh tokens antigos não voltem a valer se a conta for reativada. Reativar não incrementa.
- **No-op explícito**: status/papel igual ao atual → 200 com o estado atual e **sem** audit log.
- **`PATCH /admin/users/:id/role` só promove para `admin`** (`role: z.literal('admin')`). Alvo já admin → no-op; alvo super_user → 409 apontando para `/admin/admins/:id/role`; conta não ativa → 409 (não se dá papel administrativo a conta banida/inativa).
- **`reason` opcional** (≤ 500) nas rotas de status/papel, gravado no `metadata` do audit log.
- **Estatísticas agregadas direto do admin repository** (`userStats`): planilhas não removidas, sessões (total e concluídas), atividades, exercícios custom, conquistas, desafios e `lastActivityAt` (máx. `performedAt` entre sessões e atividades). Mesmo precedente de `calendar`/`progress`, que agregam tabelas de outras features: passar por N services só para `count()` não protegeria regra nenhuma.
- **Nunca expõe `passwordHash`/`tokenVersion`**: o detalhe traz `authMethods: { password: boolean, oauthProvider }`.
- **Busca `q`** em email e `displayName`, case-insensitive; ordenação `createdAt desc, id desc`.

## APIs

| Método | Rota                      | Papel      | Descrição                        |
| ------ | ------------------------- | ---------- | -------------------------------- |
| GET    | `/admin/users`            | admin      | `?q=&status=&role=&page=&limit=` |
| GET    | `/admin/users/:id`        | admin      | Perfil + `authMethods` + `stats` |
| PATCH  | `/admin/users/:id/status` | admin      | `{ status, reason? }`            |
| PATCH  | `/admin/users/:id/role`   | super_user | `{ role: 'admin', reason? }`     |

## Modelo de dados

Sem tabelas novas. Usa `users.status`, `users.role`, `users.token_version` e grava em `admin_audit_logs` (`user.status_changed`, `user.role_changed`).

## Variáveis de ambiente

Nenhuma nova.

## Como testar

```bash
curl -s "localhost:3333/admin/users?q=ana&status=active" -H "authorization: Bearer $ADMIN"
curl -s -X PATCH localhost:3333/admin/users/$ID/status -H "authorization: Bearer $ADMIN" \
  -H 'content-type: application/json' -d '{"status":"banned","reason":"spam"}'
```

Automatizado (`test/admin-users.test.ts`): busca por email/nome, filtros, paginação, sem vazamento de hash; stats; ban derruba sessão e incrementa `tokenVersion`; reativação; no-op sem log; matriz admin × admin/super_user (403) e super_user (200); própria conta 403; promoção, escalada por admin bloqueada, 409 de super_user/conta inativa.
