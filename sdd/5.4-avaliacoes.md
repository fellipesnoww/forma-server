# 5.4 Avaliações do app

> Roadmap: [roadmap-backend.md](../roadmap-backend.md) › Fase 5 › 5.4 Avaliações do app
> Data: 2026-10-05
>
> Feature nova e independente: qualquer usuário (web ou mobile) envia uma avaliação do app — nota
> de 1 a 5, observação opcional, plataforma e aparelho. Só o painel admin lê as avaliações.

## Decisões técnicas

- **Escrita e leitura em pacotes separados.** O envio é do usuário (`features/ratings/`); a leitura vive em `features/admin/ratings/` e é registrada no escopo encapsulado de `/admin`, então herda `authenticate` + `requireRole('admin')` sem guard por rota. `requireRole` é hierárquico: admin e super_user leem, user recebe 403. A matriz de `test/admin-access.test.ts` (montada pelo `/docs/json`) passou a cobrir a rota automaticamente.
- **Qualquer papel pode avaliar.** `POST /ratings` usa só `authenticate`; admin e super_user também são usuários do app.
- **`date` definida pelo servidor** (`DEFAULT now()`), não pelo client: evita avaliações "no passado" ou relógio errado do aparelho. Exposta como `date` (ISO 8601 UTC), como pedido na especificação.
- **Nota inteira 1–5 validada em duas camadas**: Zod na API e `CHECK (rank BETWEEN 1 AND 5)` adicionado à mão na migration (o Prisma não modela CHECK). Coluna `SMALLINT`.
- **Observação opcional** (até 2000 caracteres). Texto vazio ou só espaços vira `null`, então o client não precisa diferenciar omitir de mandar `''`.
- **`device` livre e obrigatório** (até 120 caracteres): o client monta a string (ex.: `iPhone 15 · iOS 26.1`, `Chrome 140 · Windows 11`). Não há parsing de user agent no servidor.
- **Várias avaliações por usuário**, sem edição nem remoção: cada envio é uma linha (histórico de satisfação ao longo do tempo). Abuso fica a cargo do rate limit global.
- **`averageRank` do filtro inteiro**, não só da página, calculado no mesmo `$transaction` da listagem via `aggregate` (`_count` + `_avg`), arredondado a 2 casas; `null` sem linhas.
- **Ordenação `date desc, id desc`**: `id` desempata avaliações do mesmo milissegundo (paginação estável, mesmo padrão do audit log).
- **Sem audit log**: a rota admin é só leitura; o log registra mutações.
- **Cascade em `user_id`**: apagar a conta apaga as avaliações dela, como o resto dos dados do usuário.

## APIs

| Método | Rota             | Descrição                                                                                                    |
| ------ | ---------------- | ------------------------------------------------------------------------------------------------------------ |
| POST   | `/ratings`       | `{ rank, observation?, platform, device }` → 201 `{ id, rank, observation, platform, device, date }`         |
| GET    | `/admin/ratings` | `?page&limit&platform&rank&userId&from&to` → `{ items, total, page, limit, averageRank }` (admin/super_user) |

Item da listagem admin: `{ id, user: { id, email, displayName }, rank, observation, platform, device, date }`.

Limites: `rank` inteiro 1–5; `observation` até 2000; `device` 1–120 (trim); `platform` `mobile` | `web`.
`from`/`to` são ISO 8601 com offset e inclusivos.

## Modelo de dados

- **`ratings`**: `id`, `user_id` (FK `users`, cascade), `rank` (`SMALLINT`, `CHECK 1–5`), `observation` (`VARCHAR(2000)?`), `platform` (`rating_platform`), `device` (`VARCHAR(120)`), `date` (`TIMESTAMPTZ(3)`, default `now()`). Índices `(date)` para a listagem geral e `(user_id, date)` para o filtro por usuário.
- Enum **`rating_platform`**: `mobile`, `web`.

## Como testar

```bash
curl -s -X POST localhost:3333/ratings -H "authorization: Bearer $ACCESS" -H 'content-type: application/json' \
  -d '{"rank":5,"observation":"Muito bom","platform":"mobile","device":"iPhone 15 · iOS 26.1"}'
# Com token de admin/super_user:
curl -s "localhost:3333/admin/ratings?platform=mobile&limit=10" -H "authorization: Bearer $ADMIN"
# Dados de exemplo: yarn seed:demo (5 avaliações entre os 3 usuários de demo)
```

Automatizado (`test/ratings.test.ts`): criação com data do servidor e dono correto; admin e
super_user também avaliam; observação omitida/vazia/null → `null`; 9 validações (nota 0, 6,
fracionada, ausente; plataforma desconhecida; device ausente, vazio, longo; observação longa); 401
sem token; CHECK do banco recusa nota 7 inserida direto. Listagem: 403 para user, 401 sem token,
admin e super_user leem, ordem mais recente primeiro com dados do usuário, `averageRank` do filtro,
filtros por plataforma/nota/período, paginação mantendo total e média, lista vazia, filtros
inválidos → 400.
