## Decisões técnicas

- **Guards no escopo, não na rota.** `registerAdminRoutes` abre um plugin encapsulado com prefixo `/admin` e registra `onRequest: authenticate` + `onRequest: requireRole('admin')`. Toda rota registrada ali herda o guard — não existe "esquecer o guard" numa rota admin nova. As exclusivas de super_user ficam num plugin filho que soma `requireRole('super_user')`; hooks do pai rodam antes, então a ordem é sempre 401 → 403 de papel.
- **Papel do banco prevalece sobre a claim do JWT.** `findUserStatus` virou `findUserAccess` (status + role numa só consulta por PK, a mesma que já existia) e `authenticate` grava `request.user.role = access.role`. Sem isso, um admin rebaixado continuaria admin por até 15 min (TTL do access token), e um usuário promovido precisaria relogar. Custo: zero consultas extras.
- **Audit log transacional.** `runAudited(actorId, (tx, log) => ...)` abre `prisma.$transaction` interativa; o callback usa `tx` em toda escrita e chama `log({ action, targetType, targetId, metadata })`. Se a mutação falhar, nada é logado; se o insert do log falhar, a mutação é desfeita. Quando o service decide que é no-op (ex.: status igual ao atual), simplesmente não chama `log`.
- **Catálogo fechado de ações** (`AUDIT_ACTIONS` em `audit.schemas.ts`): `exercise.created|updated|status_changed`, `muscle_group.created|updated`, `user.status_changed|role_changed`, `achievement.created|updated|deleted`, `challenge.created|updated|deleted`. É contrato do filtro `?action=`; ação nova entra lá antes de ser gravada.
- **`metadata` JSONB** com `from`/`to` (status, papel) ou `before`/`after` (snapshots enxutos de catálogo). `reason` opcional enviado nas rotas de status/papel também vai para o metadata.
- **`actor_id` em `SET NULL`**: apagar a conta de um admin não apaga o que ele fez. `null` também identifica ações fora da API (`yarn user:set-role`, ver 3.6). `target_id` sem FK porque aponta para tabelas diferentes conforme `target_type`.
- **`TransactionClient`** exportado de `shared/db/client.ts`: repositories admin recebem o cliente da transação em vez de usar o singleton. `PrismaClient` também satisfaz o tipo, então leituras fora de transação reaproveitam as mesmas funções.
- **Schemas comuns** em `features/admin/admin.schemas.ts`: envelope de erro, `idParams`, `paginationQuerySchema` (`page` ≥ 1, `limit` 1..100, default 20) e `paginated(item)` → `{ items, total, page, limit }`, conforme a convenção de paginação admin do roadmap.
- **`no-underscore-dangle`** passou a permitir `_count`/`_max`/... — são nomes da API do Prisma, usados pela primeira vez nas agregações admin.

## APIs

Nenhuma rota própria da 3.1 — ela entrega o namespace. Rotas em 3.2–3.5.

| Escopo     | Guard                                   | Rotas                                                                                                                     |
| ---------- | --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| admin      | `authenticate` + `requireRole('admin')` | `/admin/exercises*`, `/admin/muscle-groups*`, `/admin/users*` (exceto role), `/admin/achievements*`, `/admin/challenges*` |

## Modelo de dados

**`admin_audit_logs`** (nova): `id` (uuid pk), `actor_id` (fk nullable → `users.id`, `ON DELETE SET NULL`), `action` (varchar 64), `target_type` (varchar 40), `target_id` (uuid nullable, sem FK), `metadata` (jsonb nullable), `created_at`. Índices `(created_at)`, `(actor_id, created_at)`, `(action, created_at)`, `(target_type, target_id)`.

## Como testar

```bash
ADMIN=$(yarn --silent token:dev --role=admin --sub=<uuid de um admin real>)
curl -s localhost:3333/admin/users -H "authorization: Bearer $ADMIN"          # 200
USER=$(yarn --silent token:dev --sub=<uuid de um user>)
curl -s localhost:3333/admin/users -H "authorization: Bearer $USER"           # 403
```

> `token:dev` só assina o token: como o papel agora vem do banco, `--role=admin` com o `sub` de uma conta `user` recebe 403. Use `yarn user:set-role` para mudar o papel da conta.

Automatizado: `test/admin-access.test.ts` lê `/docs/json`, pega todas as rotas `/admin/*` (25) e confere: user → 403 em todas; admin → 403 exatamente nas 4 de super_user; super_user → nunca 403; admin banido → 403 de conta; rebaixamento/promoção valem com o mesmo token.
