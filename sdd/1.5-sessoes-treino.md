## Decisões técnicas

- **`sheet_id` obrigatório**: a 1.5 é "execução de treino" de uma planilha; atividades livres sem planilha são a Fase 2.1 e terão modelo próprio. Na criação, a planilha precisa estar ativa e pertencer ao usuário (`activeSheetBelongsToUser`, exportado por `features/workout-sheets/index.ts`) — caso contrário 400, igual à regra de referência a exercício da 1.4.
- **Sessão não aponta para `sheet_exercises`**: `session_exercises` guarda a própria referência (`exercise_id`/`custom_exercise_id`) em vez de um FK para o item da planilha. O usuário pode trocar ou adicionar exercícios durante a execução, e a planilha pode ser editada depois (o `PATCH` da 1.4 recria os `sheet_exercises`) sem reescrever o histórico.
- **Planilha removida não apaga histórico**: o soft delete de `workout_sheets` não toca as sessões; detalhe e listagem continuam retornando `sheetName`. O FK `sheet_id` usa `onDelete: Cascade` só para o caso de exclusão física via usuário (cascade de `users`).
- **`performedAt` no futuro é rejeitado** (400), com 5 min de tolerância para relógio do client adiantado. O roadmap só pede "aceita valor passado"; uma sessão datada no futuro quebraria o histórico e o calendário da Fase 2.2.
- **`completedAt` separado de `performedAt`**: `performedAt` é "quando treinou" (editável, retroativo) e é o eixo dos filtros `from`/`to`; `completedAt` é "quando a sessão foi finalizada no app" e é o que torna `complete` idempotente.
- **Idempotência de `complete`**: se `completedAt` já existe, a rota devolve 200 com o estado atual (mesmo `completedAt` original), sem 409. A escrita usa `updateMany where completedAt IS NULL`, então duas chamadas concorrentes não sobrescrevem o horário da primeira.
- **`PATCH` substitui exercícios+séries por completo** (mesma estratégia do `PATCH` de planilhas, 1.4): `deleteMany` + recriação numa transação. Continua permitido após `complete` — correção retroativa é parte do produto.
- **Foto: upload por rota dedicada, remoção pelo `PATCH`**: `POST /:id/photo` recebe base64 como `POST /profile/avatar`. No `PATCH`, `photoUrl` só aceita `null` (remove); aceitar uma URL arbitrária ali deixaria o client apontar a sessão para mídia de outro usuário.
- **`sheetId` em camelCase na query** (não `sheet_id` como no texto do roadmap): segue o padrão já entregue em `GET /exercises?muscleGroup=`.
- **Listagem paginada** (`page`/`limit`, máx. 100, ordenada por `performedAt desc`) no mesmo formato de `GET /profile/measurements`: o histórico cresce sem limite.

## APIs

| Método | Rota                             | Descrição                                                            |
| ------ | -------------------------------- | -------------------------------------------------------------------- |
| GET    | `/workout-sessions`              | Histórico paginado (`?from=&to=&sheetId=&page=&limit=`)              |
| POST   | `/workout-sessions`              | Registra sessão com exercícios e séries                              |
| GET    | `/workout-sessions/:id`          | Detalhe (exercícios com nome resolvido + séries)                     |
| PATCH  | `/workout-sessions/:id`          | Atualiza `performedAt`, `comment`, remove foto e/ou substitui séries |
| POST   | `/workout-sessions/:id/complete` | Finaliza a sessão (idempotente)                                      |
| POST   | `/workout-sessions/:id/photo`    | Upload base64 da foto pós-treino, retorna `{ photoUrl }`             |

## Modelo de dados

**`workout_sessions`** (nova): `id` (uuid pk), `user_id` (fk → `users.id`, cascade), `sheet_id` (fk → `workout_sheets.id`, cascade), `performed_at` (timestamptz, default `now()`), `photo_url` (nullable), `comment` (varchar 1000, nullable), `completed_at` (nullable), `created_at`, `updated_at`. Índices `(user_id, performed_at)` e `(sheet_id)`.

**`session_exercises`** (nova): `id` (uuid pk), `session_id` (fk → `workout_sessions.id`, cascade), `exercise_id` (fk nullable → `exercises.id`), `custom_exercise_id` (fk nullable → `custom_exercises.id`), `sort_order` (int). Índice `(session_id, sort_order)`.

**`session_sets`** (nova): `id` (uuid pk), `session_exercise_id` (fk → `session_exercises.id`, cascade), `set_number` (int), `reps` (int), `weight_kg` (double), `completed` (bool, default false). Único `(session_exercise_id, set_number)`.

```bash
yarn db:up && yarn db:migrate && yarn db:seed && yarn dev

ACCESS=...      # login como na 1.4
SHEET_ID=...    # POST /workout-sheets
EXERCISE_ID=... # GET /exercises?q=...

curl -s -X POST localhost:3333/workout-sessions -H "authorization: Bearer $ACCESS" \
  -H 'content-type: application/json' -d "{\"sheetId\":\"$SHEET_ID\",\"comment\":\"bom treino\",
    \"exercises\":[{\"exerciseId\":\"$EXERCISE_ID\",\"sortOrder\":0,\"sets\":[
      {\"setNumber\":1,\"reps\":10,\"weightKg\":40,\"completed\":true},
      {\"setNumber\":2,\"reps\":8,\"weightKg\":40}]}]}"

curl -s -X POST localhost:3333/workout-sessions/$SESSION_ID/complete -H "authorization: Bearer $ACCESS"
curl -s "localhost:3333/workout-sessions?from=2026-09-01T00:00:00Z&sheetId=$SHEET_ID" -H "authorization: Bearer $ACCESS"
```

Cenários executados manualmente (24, todos com o status esperado): criação com exercício de
catálogo + custom, detalhe, criação retroativa (`performedAt` passado → 201), `performedAt` futuro
→ 400, `reps` negativo → 400, `weightKg` negativo → 400, `setNumber` duplicado → 400, planilha de
outro usuário → 400, detalhe por outro usuário → 404, `PATCH` de comentário (`null`) + séries,
`PATCH` vazio → 400, `complete` duas vezes (mesmo `completedAt`), upload de foto PNG → 200, MIME
não permitido → 415, foto em sessão de outro usuário → 404, remoção de foto via `PATCH`, listagem
geral, filtro `from`/`to`, filtro `sheetId` + paginação, listagem de outro usuário vazia, detalhe
após soft delete da planilha → 200, criação em planilha removida → 400, sem token → 401.

Automatizado (`yarn test`, arquivo `test/workout-sessions.test.ts`):

| Grupo       | Casos                                                                                                                                                                        |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| performedAt | default = agora; passado aceito; offset de fuso normalizado para UTC; +2 min aceito; +10 min → 400 no POST e no PATCH; formato não ISO → 400                                 |
| Séries      | `reps`/`weightKg` = 0 e peso fracionado aceitos; `completed` default false; reps negativo/fracionado, peso negativo, `setNumber` 0 ou duplicado, sem séries → 400; ordenação |
| Referências | ambos/nenhum exercício, `exerciseId`/`sheetId` inexistentes → 400; planilha e custom exercise removidos bloqueiam sessão nova mas o histórico segue legível                  |
| Comentário  | 1000 aceito, 1001 → 400; `null` no PATCH limpa                                                                                                                               |
| PATCH       | vazio → 400; `exercises` recria séries (ids novos); sem `exercises` mantém séries; mesmas validações do POST; `photoUrl` string → 400; permitido após `complete`             |
| complete    | nasce em andamento; repetido devolve o `completedAt` original; 5 chamadas concorrentes geram um único `completedAt`; não altera `performedAt`                                |
| Foto        | associa e o binário é baixável; prefixo data URL aceito; novo upload substitui; `photoUrl: null` remove; MIME fora da lista → 415; MIME diferente do conteúdo rejeitado      |
| Histórico   | ordem por `performedAt` desc; item sem `exercises`; `from`/`to` inclusivos; filtro `sheetId` e combinado; paginação e defaults; queries inválidas → 400                      |

Mutation check: tirar a idempotência de `complete` derruba 2 casos; liberar `performedAt` no futuro derruba 1.

## Pendências

- Foto sem compressão/resize: mesmo descope do avatar (1.2) e da Fase 0 — limite continua o global `MEDIA_MAX_SIZE_MB`. Item "Compressão de foto" segue aberto no roadmap.
- Trocar ou remover a foto não apaga o `media_assets` anterior (mesmo comportamento do avatar); limpeza de mídia órfã fica para quando houver storage externo.
- Exclusividade `exerciseId`/`customExerciseId` sem `CHECK` no Postgres — mesma decisão e mesmo risco registrados na 1.4.
- Não há `DELETE /workout-sessions/:id` — o roadmap não pede; entra se a Fase 2.2 (calendário/retroativo) precisar.
